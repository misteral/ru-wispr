# Licensing research: как индии-разработчики macOS защищают платный софт

**Цель документа:** понять, какие модели лицензирования используют другие
независимые разработчики macOS-приложений, прежде чем мы выберем подход для
Dikto Pro RU. Решение влияет на: можем ли мы продавать без бэкенда, насколько
сложно пиратить, какие сервисы нанимать, сколько кода писать.

**Статус:** research, не решение. После прочтения нужно сделать выбор и
обновить `dikto-pro-ru-roadmap.md`.

---

## TL;DR

Для нашей ситуации (самозанятый, нет бэкенда, мало времени, малый объём
первых продаж) **оффлайн-проверка криптоподписи** — индустриальный стандарт
у инди-разработчиков. Подписываем JSON `{email, plan, issuedAt, deviceId?}`
Ed25519 ключом, публичный ключ зашиваем в приложение, проверяем подпись
локально. Сервер не нужен.

Готовые сервисы (Keygen, Cryptolens, Paddle, Lemon Squeezy, Gumroad) делают
то же самое плюс берут на себя выдачу ключей и платежи — но все они не очень
дружат с самозанятым в РФ и берут комиссию 5–10%. DIY-вариант на Ed25519 —
50 строк Swift и 30 строк CLI.

## Четыре основных паттерна

### 1. Honor system (доверие)

Платишь — получаешь key. App не проверяет, можно ли вообще пользоваться.

| Кто использует | Замечания |
|---|---|
| Sublime Text (классика) | До 2024 приложение работало и без ключа, только показывало "UNREGISTERED" в title |
| BBEdit | Можно работать без лицензии в "free mode" с урезанными фичами |
| Многие mini-инди-приложения | Особенно тулзы для девелоперов |

**Плюсы:** ноль кода, ноль сервиса, ноль головной боли с возвратами/блокировками.
**Минусы:** не подходит для массового рынка — пиратство 99%. Работает у Sublime,
потому что аудитория — программисты, которые понимают, что код стоит денег,
и обычно платят.

**Для Dikto Pro RU:** слишком оптимистично. Русская аудитория Mac — это инди-юзеры
+ корпорат + студенты, конверсия в честную оплату будет ниже, чем у Sublime.

### 2. Offline-проверка криптоподписи (industry standard у инди)

Лицензия — это маленький подписанный payload, например:
```json
{
  "email": "user@example.com",
  "plan": "lifetime",
  "issuedAt": "2026-05-19T10:00:00Z",
  "deviceLimit": 2
}
```
Подписывается приватным Ed25519 (или RSA-2048) ключом продавца. В app
зашит публичный ключ. На активации app локально проверяет подпись и
сохраняет лицензию в Keychain.

| Кто использует | Реализация |
|---|---|
| **Bear (notes)** | Лицензия = подписанная JSON-строка, проверка локальная |
| **iA Writer** | Аналогично, плюс периодический online-чек |
| **Tot (The Iconfactory)** | Подписанные ключи, без сервера |
| **Capo (audio learning)** | Подписи + revocation list |
| **Acorn (image editor)** | Свой формат подписанных лицензий |
| **MarkdownEdit, Cardhop, Fantastical (старые версии)** | Все используют offline crypto |
| **NetNewsWire (open source)** | App Store + offline keys для прямой продажи |

**Плюсы:**
- Сервер не нужен — продавать можно с любого статического хостинга.
- Активация работает в самолёте и без сети.
- Cryptographically secure: чтобы пиратить, надо взломать Ed25519 (никто не пытается на инди-уровне) ИЛИ декомпилировать app и зашить свой публичный ключ (требует ребилда binary, теряется подпись Apple).
- Покупателю не нужно создавать аккаунт.

**Минусы:**
- **Revocation тяжёлая.** Если ключ утёк в торрент — для отзыва нужен online-blocklist. Можно: app раз в неделю качает с CDN короткий JSON со списком отозванных ключей. Это минимальный online-компонент, без сложного бэкенда.
- Нет цифр сколько у тебя активных пользователей (если не сделать опциональную телеметрию).
- Device-limit невозможно проверить без сервера: лицензия с лимитом «2 устройства» всё равно может быть установлена на 100, локальная проверка этого не отловит. На практике инди-разработчики просто игнорируют это или вводят offline-only "honor" лимит ("при установке более чем на 2 устройства мы оставляем за собой право заблокировать").

**Для Dikto Pro RU:** **рекомендуемый вариант для первых продаж.** Закрывает 95% пиратства, не требует бэкенда, легко мигрируется в гибрид позже.

### 3. Online-активация с сервером (модель из нашего исходного PRD)

App шлёт ключ серверу, сервер проверяет в БД и выдаёт bearer-токен. Периодическая re-валидация раз в N дней.

| Кто использует | Замечания |
|---|---|
| **Tower (Git client)** | Online-активация, до 3 устройств, проверка раз в неделю |
| **Affinity Suite (Photo, Designer, Publisher)** | После покупки нужен online-первый-запуск |
| **Pixelmator Pro** | Только Mac App Store, так что Apple делает за них |
| **Things 3** | Mac App Store/iCloud — без явной активации |
| **CleanMyMac** (MacPaw) | Свой backend, online-активация + telemetry |
| **Sketch** | Подписочная, плюс online-чек устройств |
| **Hookmark** | Online-чек раз в неделю, offline grace period 30 дней |

**Плюсы:**
- Реальный device-limit (с reference counting).
- Можно отзывать ключи мгновенно.
- Знаешь, сколько активных лицензий — данные для бизнеса.
- Возврат через ст. 26.1 ЗоЗПП обрабатывается чисто: сервер инвалидирует, app узнаёт.

**Минусы:**
- Нужен сервер с uptime 99%+ — иначе паиющие пользователи не могут работать.
- Жалобы "интернет не работает в самолёте → ваше приложение тоже" — частая боль у Affinity/Pixelmator.
- Стоимость: $5–50/мес хостинга + время на поддержку.

**Для Dikto Pro RU:** план долгосрочно (Sprint 2-3 нашего PRD), но **не сейчас**.

### 4. Mac App Store / SetApp

Apple/Setapp полностью управляют лицензированием.

| Кто использует | Замечания |
|---|---|
| **Things 3** | App Store-only |
| **MindNode** | App Store-only |
| **OmniFocus, OmniGraffle** | App Store + direct, две модели параллельно |
| **MoneyMoney** | Только Setapp |

**Плюсы:**
- Нуль работы с лицензиями — Apple проверяет.
- Customers доверяют App Store больше, чем прямой продаже.
- Auto-update встроен.

**Минусы:**
- **Apple 30% (15% при подписке от $99/год).** На цене 1990 ₽ это 597 ₽ комиссии.
- App Sandbox обязателен — Dikto использует accessibility и hotkeys; **не пройдёт sandbox без entitlements которые Apple не любит давать.**
- Долгое review (3–7 дней).
- Apple ID требуется покупателю.
- Setapp платит фиксированную долю по проценту использования — для нового нишевого приложения это копейки.
- Российская аудитория хуже покупает в App Store с российских карт.

**Для Dikto Pro RU:** проблематично — sandbox несовместим с глобальной горячей клавишей и текст-инжекцией. И русские карты часто не работают в App Store. **Не подходит.**

## Готовые сервисы (License-as-a-Service)

Если не хочешь возиться с Ed25519 самостоятельно — есть managed-варианты.
Все они построены на одном из паттернов выше плюс предоставляют веб-кабинет.

### Keygen.sh

| | |
|---|---|
| Модель | Online API + offline-токены |
| Цена | $39/мес (Lite) до $199+/мес (Pro), free до 50 ключей |
| Плюсы | Современный API, открытый исходный код, поддерживает self-hosted |
| Минусы | Платит в USD, нет интеграции с СБП/самозанятыми |
| Для нас | Хорош для гибрида в Stage 2-3, не для первых продаж |

### Cryptolens

| | |
|---|---|
| Модель | License keys + offline verification SDK |
| Цена | Free до 100 активаций/мес, $9/мес дальше |
| Плюсы | SDK для Swift, поддержка floating licenses |
| Минусы | Платит в USD, UI устаревший |
| Для нас | Дешёвый, но нужен USD-биллинг |

### Paddle

| | |
|---|---|
| Модель | Merchant of Record — берёт на себя НДС, чеки, лицензии |
| Цена | 5% + $0.50 с транзакции |
| Плюсы | License framework SDK для Swift, всё под ключ |
| Минусы | Не принимают самозанятого из РФ; работают через юрлицо |
| Для нас | Слишком сложно для нашей юрформы |

### Lemon Squeezy

| | |
|---|---|
| Модель | Merchant of Record + License Keys API |
| Цена | 5% + $0.50 |
| Плюсы | Современная админка, License Keys API |
| Минусы | Та же история — не работает с РФ-самозанятыми |
| Для нас | Нет |

### Gumroad

| | |
|---|---|
| Модель | Платёжная платформа + опциональные License Keys |
| Цена | 10% (без подписки) |
| Плюсы | License Keys "бесплатно" (внутри платформы) |
| Минусы | Не работает с РФ-самозанятыми, ставят 10% |
| Для нас | Нет |

### Lava.top (наш текущий выбор PSP)

| | |
|---|---|
| Модель | PSP + опционально доставка цифровых файлов |
| Цена | ~5% |
| Плюсы | Работает с самозанятыми РФ, СБП, авточеки НПД, доставка digital-продукта |
| Минусы | License Keys API нет — нужно либо генерить ключи у себя и отдавать Lava в "содержимое цифрового товара", либо использовать как trigger для своего бэкенда |
| Для нас | **Хорошо** — берём в primary, генерим ключи отдельно |

## Как сделать DIY на Ed25519 (стандарт инди)

Это паттерн, который используют Bear, Tot, iA Writer и десятки других. ~50 строк
Swift + ~30 строк CLI для выдачи. Можно реализовать за полдня.

### Архитектура

```
┌──────────────────────────┐
│  License generation CLI  │  локально, у разработчика
│  (apps/macos/scripts/    │
│   issue-license.swift)   │  ed25519 private key (НЕ в git)
└────────────┬─────────────┘
             │ генерит подписанный JSON
             ▼
   ┌─────────────────────────────┐
   │   licence.diktoproru        │
   │   { email, plan, issuedAt,  │
   │     sig: ed25519(...) }     │
   └─────────────────────────────┘
             │
             │ отправляется покупателю на email вручную
             │ (потом автоматизируется в backend Sprint 2)
             ▼
   ┌──────────────────────────┐
   │  Dikto Pro app           │
   │  - public key embedded   │
   │  - verify signature      │
   │  - store in Keychain     │
   │  - check expiry locally  │
   └──────────────────────────┘
```

### Что в коде

1. **Public Ed25519 key зашит в `ProductFlavor.swift`** (32 байта).
2. **Activation flow:**
   - Пользователь вставляет JSON-ключ в окно активации (или дабл-кликает по `.diktoproru` файлу, который открывается по URL scheme).
   - Приложение проверяет Ed25519 подпись через `CryptoKit.Curve25519.Signing.PublicKey.isValidSignature`.
   - Если валид — сохраняет в Keychain как `LicenseRecord`.
3. **Optional revocation list** (когда будет CDN/бэкенд):
   - Раз в 7 дней app качает `https://dikto.itbeaver.co/revoked.json`.
   - Если текущий ключ там — статус → `.invalid("revoked")`.

### Что в "сервере" (читай: у нас на ноуте)

CLI скрипт `apps/macos/scripts/issue-license.swift`:

```swift
// swift run issue-license email@example.com lifetime
// → выводит signed JSON в stdout
// → копируем, шлём покупателю через email
```

Private key хранится в Keychain разработчика (или в `~/.dikto/private.key`
с `chmod 600`). НЕ коммитится в git.

### Migration path

Когда понадобится сервер:
- Online-активация добавляется как ВТОРОЙ путь рядом с offline (offline-keys продолжают работать).
- Backend начинает выдавать ключи автоматически после Lava webhook.
- Revocation list публикуется на статике CDN.

То есть выбор offline-keys сейчас **не закрывает** дверь к серверу — это
постепенная миграция.

## Рекомендация для Dikto Pro RU

**Для первых продаж (v1.0):** реализовать DIY Ed25519 offline-keys. Удаляем
зависимость `LicenseClient.swift` от сетевых вызовов, делаем `LicenseManager`
проверяющим подпись локально. Добавляем CLI скрипт для генерации ключей.
Лицензии шлём покупателям вручную после уведомления от Lava (или Lava сама
доставляет ключ как "цифровой товар").

**Когда: после 30 первых продаж** или когда мы решим автоматизировать
бэкенд по issue ключа. Тогда:
1. Поднимаем сервер по `backend-prd.md`.
2. Сервер начинает выдавать те же подписанные оффлайн-ключи автоматически
   после webhook от Lava.
3. Параллельно добавляем revocation list на статическом CDN.
4. Только когда нужен полноценный device-tracking — добавляем `/v1/activate`
   и `/v1/validate` сетевые эндпоинты. App может поддерживать оба пути
   (offline + online).

**Аргументы:**
- Закрывает 95% пиратства, что достаточно для нишевого продукта на $20.
- Не блокирует первые продажи неделей бэкенд-разработки.
- Совместимо с нашей юрформой (Lava принимает самозанятого).
- Миграция в online — постепенная, без перевыкатывания всей user-базы.
- Покупатели не сталкиваются с "интернет упал → программа сломалась".

**Аргумент против (учесть, если несогласны):**
- Если планируем активно продавать корпоративам с device-tracking требованиями — offline-keys не дадут жёстко ограничить количество устройств, и придётся переходить на online раньше.

## Что я НЕ рекомендую и почему

- **Honor system** — слишком оптимистично для нашей аудитории и цены.
- **App Store** — несовместимо с архитектурой Dikto (нужен sandbox, accessibility, hotkeys).
- **Paddle/Lemon Squeezy** — не работают с РФ-самозанятыми.
- **Keygen.sh/Cryptolens** — нормально технически, но платить в USD каждый месяц за то, что можно сделать в 50 строк Swift, — overkill для первой версии.

---

## Открытые вопросы для решения

1. **Готовы ли мы жить с тем, что технически device-limit не enforce-ится на уровне приложения?** Если да → offline keys. Если нет → online с самого начала, ждём 2-3 недели бэкенда.
2. **Кто генерит ключ для первого покупателя?** Lava уведомит на email → мы вручную запускаем CLI → шлём ключ в ответном письме. Готовы к ручному режиму первые 10–50 продаж?
3. **Что если ключ утёк?** Без revocation list — никак не отозвать. Готовы пережить это в первые месяцы?
4. **Размер ключа имеет значение?** Ed25519-подпись + JSON получится ~250 символов в base64. Это «копировать-вставить» friendly, но не «одно слово».
